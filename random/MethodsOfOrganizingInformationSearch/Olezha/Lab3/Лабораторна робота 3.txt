ЛАБОРАТОРНА РОБОТА №3. ПОШУК ДОКУМЕНТІВ ЗА МЕТАДАНИМИ ЗА ДОПОМОГОЮ ELASTICSEARCH
    Мета роботи: отримати практичні навички розроблення інформаційно- пошукової системи (з пошуком за метаданими), інтегрованої з системою Elasticsearch.
Теоретичні відомості
Загальна інформація про стек Elastic та Elasticsearch
    Elastic Stack - це набір програмного забезпечення з відкритим вихідним кодом, що є інтегрованими між собою та слугують для ефективного збирання, перетворення, збереження, пошуку та візуалізації даних. Початково даний набір продуктів називався ELK (від перших букв трьох початкових програмних продуктів - Elasticsearch, Logstash, Kibana) та був розроблений для ефективного збору, збереження та аналізу неструктурованих журналів виконання ("логів") програмного забезпечення. Пізніше до трьох продуктів було розроблено та приєднано четвертий - Beats.
Основними варіантами використання продуктів Elastic Stack є:
* Робота з великими даними (big data).
* Інтеграція у інформаційно-пошукові системи зі складними вимогами до пошуку та його ефективності.
* Централізований збір журналів виконання програмного забезпечення.
* Моніторинг безпекових даних.
    За збереження та пошук даних у даному наборі програмного забезпечення відповідає продукт Elasticsearch - пошуковий сервер, розроблений на основі Apache Lucene, та який надає RESTful API для виконання основних налаштувань та пошукових запитів.
Встановлення Elasticsearch
    Elasticsearch надає наступні варіанти встановлення на власному комп'ютері:

* .tar.gz архіви для встановлення на будь-якому дистрибутиві Linux чи MacOS;
* .zip архів для встановлення на операційній системі Windows;
* deb пакет для встановлення на Debian, Ubuntu чи будь-якому іншому дистрибутиві Linux на основі Debian;
* rpm пакет для встановлення на Red Hat, Centos, SLES, OpenSuSE чи будь- якому іншому дистрибутиві Linux, що використовує RPM;
* docker образ для запуску у контейнері.

Створення та налаштування індекса
    Після встановлення та запуску Elasticsearch для збереження та пошуку документів необхідно створити один або декілька індексів. Якщо порівнювати Elasticsearch з традиційними базами даних SQL, то індекс можливо прирівняти до таблиці, де зберігаються дані одного виду; тоді документ - це один запис у таблиці.
    Найпростіший варіант створення індекса виглядає як відсилання HTTP- запиту з порожнім тілом наступного виду, де <name> - обране ім'я індекса:

    Також слід звернути увагу на те, що якщо Elasticsearch встановлено з налаштуваннями за замовчуванням, то з запитом обов'язково необхідно відправити також автентифікаційні дані: ім'я користувача за замовчуванням elastic та згенерований для нього пароль. Для цього використовується механізм HTTP Basic Authentication.
Elasticsearch має наступні обмеження на можливі імена індексів:
* допускаються літери тільки нижнього регістру;
* ім'я не може включати пробіл чи наступні спеціальні символи: \, /, *, ?, ", <, >, |, ,, #, :;
* ім'я не може починатися з наступних символів (але може їх включати на інших позиціях): -, _, +, .;

* ім'я не може бути довшим, ніж 255 байтів (рахуються саме байти, тому не латинські символи в імені будуть рахуватися за два чи навіть більше байти).
    Наведений вище запит створить індекс з налаштуваннями за замовчуванням та динамічним відображенням (mapping). Відображення визначає, як документ та поля, з яких він складається, буде зберігатися та індексуватися. У випадку динамічного відображення його підтримувати та оновлювати буде сам Elasticsearch - при індексуванні нових документів тип полів буде автоматично визначатися та зберігатися у визначенні відображення.
    Хоча динамічним відображенням зручно користуватися при прототипіюванні, більш правильним підходом є задання явного відображення під час створення індекса. Даний підхід надає можливість тонкого налаштування відображення розробнику, що створює індекс: назви і типи полів, які текстові поля призначені для повнотекстового пошуку, формат значень дати, тощо.
    Для задання явного відображення під час створення індекса, у тіло запиту додається об'єкт з полем mappings, значення якого - об'єкт з налаштуваннями відображення відповідно до документації Elasticsearch. Наведений нижче запит створює індекс з назвою movies, у відображенні якого задано чотири поля для документа різних типів:


    Elasticsearch підтримує велику кількість базових та спеціалізованих типів полів, включаючи, але не обмежуючись:
* binary - бінарне значення, кодоване за допомогою base64;
* boolean - булеве значення (true або false);
* long, integer, short, byte, double, float, half_float, scaled_float, unsigned_long - числові типи різної точності та розмірності;
* date - дата і час;
* keyword - текстове поле для пошуку за повним співпадінням;
* text - текстове поле для повнотекстового пошуку;
* object - вкладений об'єкт;
* ip - IP-адреса;
* version - версія програмного забезпечення (відповідно до Semantic Versioning).
    Elasticsearch не має виділеного типу для масивів - поле будь-якого типу може містити нуль, одне або декілька значень цього типу у вигляді масиву. Наприклад, поле типу integer може містити будь-яке з наступних значень: 1, [1, 2], [1, [2, 3]] (це значення аналогічне до [1, 2, 3] - Elasticsearch автоматично розкриває масиви масивів).

Виконання запитів
    Для виконання запитів Elasticsearch надає окрему предметно-специфічну мову під назвою "Query DSL", яка побудована на основі JSON. Запит, виражений за допомогою Query DSL, можна порівняти з абстрактним синтаксичним деревом, що містить два типи вузлів:
* листкові запити - запити, що шукають певне значення у певному полі;
* складені запити - запити, що обгортають інші складені запити або листкові запити.
    Запити у Elasticsearch виконуються за допомогою окремої кінцевої точки API POST /<index>/_search. Об'єкт, що необхідно передавати у тілі запиту до даної кінцевої точки, може містити багато різних параметрів, що впливають чи налаштовують пошук, але у більшості випадків достатньо використовувати параметр query, в якому передається власне запит. Приклад такого запиту наведено нижче (даний запит шукає документи, чиє поле title має значення
"Fast X" - див. далі пункт "Прості запити на рівні терма"):

У відповіді для кожного знайденого документа також доступне поле
_score - оцінка релевантності документа запиту, яка розраховується автоматично Elasticsearch для будь-якого запиту. Для запитів, які шукають документи лише з повним співпадінням, така оцінка може не мати сенсу, але все одно буде розрахована через те, що більшість запитів виконуються за замовчуванням у контексті запитів. Існує також інший контекст - контекст фільтрів - який доцільніше використовувати для запитів на повне співпадіння, але він доступний лише для вкладених запитів у певні складені запити, які будуть розглянуті пізніше (див. далі пункт "Найпростіші складені запити").

Прості запити на рівні терма
    Найбільш поширеною групою запитів на пошук повного співпадіння (фільтрацію), які підтримує Elasticsearch, є запити на рівні терма.
    Запит IDs знаходить документи за їх унікальними ідентифікаторами (тут і далі для прикладів запитів наводиться лише сам об'єкт запиту, який встановлюється як значення поля query у тілі HTTP запиту):

    У відповідь будуть повернуті ті документи, чиї унікальні ідентифікатори потрапляють у переданий масив values. Якщо у масиві values вказати неіснуючий ідентифікатор, помилки повернуто не буде.
Даний запит має лише один параметр - власне масив рядків values
(обов'язковий).
    Запит Exists знаходить документи, що містять будь-яке індексоване значення для вказаного поля. Якщо певний документ для вказаного поля містить значення null або [], то таке значення вважається неіндексованим (але порожній рядок "" вважається індексованим значенням):

    Даний запит має лише один параметр - рядок field, в якому вказується назва поля, по якому відбувається пошук (обов'язковий).
    Запит Term шукає документи, що містить точне значення вказаного терма у вказаному полі. Даний запит можливо використовувати для полів будь-якого типу, проте загальною рекомендацією є уникання його використання для полів типу text. Це пов'язано з тим, що поля такого типу призначені для повнотекстового пошуку, тому для них зберігається значення після аналізу тексту (див. далі "Теоретичні відомості" лабораторної роботи №4). Тому якщо

документ містить рядки, по яким потрібно виконувати пошук за повним співпадінням, то для таких полів варто використовувати поля типу keyword.

    На верхньому рівні даний запит має лише один параметр, назва якого повинна співпадати з назвою поля, за яким відбувається пошук (обов'язковий). Значенням для цього параметра виступає об'єкт, який у свою чергу також може містити обов'язкові і, за необхідності, необов'язкові поля:
* value - значення для пошуку (обов'язковий);
* case_insensitive - булеве поле: якщо має значення true, то пошук є нечутливим до	регістру символів;	якщо	має	значення false, то чутливість	до	 регістру	символів		визначається	налаштуваннями відображення поля (необов'язкове; значення за замовчуванням - false).
    Запит Terms знаходить документи, які містять одне чи більше точних значень вказаних термів у вказаному полі. Запит Terms такий самий, як запит Term, за винятком того, що можна шукати декілька значень. Документ буде відповідати запиту, якщо він містить хоча б один із термів у вказаному полі:



    Обов'язковим параметром даного запиту є параметр, назва якого повинна співпадати з назвою поля, за яким відбувається пошук; значенням даного параметру  є  масив,  що  містить  значення  термів,  що  шукаються.  За
замовчуванням, Elasticsearch обмежує максимальну довжину даного масиву

65536 термами; за необхідності це значення можливо змінити, використовуючи налаштування  індекса  index.max_terms_count.
    Запит Terms_set є подібним до запиту Terms, проте він дозволяє встановити мінімальну кількість термів, яку документ повинен містити у вказаному полі, щоб він вважався відповідним запиту. Такий запит може бути корисним при роботі з полями, що містять масиви значень.

Складні ("дорогі") запити на рівні терма
    Деякі із запитів на рівні терма, які підтримує Elasticsearch, можуть виконуватися повільно. Це пов'язано з їх природою - для них важко реалізувати повноцінний індекс для пришвидшення пошуку або їх виконання потребує великої кількості виконання внутрішніх, прихованих запитів. За замовчуванням Elasticsearch підтримує виконання таких запитів, але за необхідності їх виконання можливо вимкнути за допомогою налаштування search.allow_expensive_queries для того, щоб ніхто з доступом до індекса не міг їх виконати і таким чином вплинути на швидкодію Elasticsearch.
    Запит Regexp знаходить документи, які містять значення у вказаному полі, що відповідають заданому регулярному виразу. Для написання регулярних виразів використовується синтаксис Apache Lucene, який підтримує більшість стандартних операторів (., ?, +, *, {}, |, (), []), а також надає деякі власні, нестандартні оператори (наприклад, <> - оператор числового інтервалу):

    На верхньому рівні, аналогічно до інших запитів, даний запит має лише один параметр, назва якого повинна співпадати з назвою поля, за яким відбувається пошук (обов'язковий). Значенням для цього параметра виступає об'єкт, який у свою чергу також може містити обов'язкові і, за необхідності, необов'язкові поля:

* value - регулярний вираз (обов'язковий); за замовчуванням, максимальна довжина регулярного виразу обмежена 1000 символами; за необхідності, дане обмеження можливо змінити за допомогою налаштування індекса index.max_regex_length;
* flags - містить перерахунок прапорців, які нестандартні оператори мають бути ввімкнутими (необов'язкове, значення за замовчуванням - ALL);
* case_insensitive - булеве поле: якщо має значення true, то пошук є нечутливим до регістру символів; якщо має значення false, то чутливість до регістру символів визначається налаштуваннями відображення поля (необов'язкове; значення за замовчуванням - false);
* max_determinized_states - для пошуку за регулярним виразом Apache Lucene перетворює його у кінцевий автомат; даний параметр регулює максимальну можливу кількість станів у такого автомата (необов'язкове, значення за замовчуванням - 10000).
    Запит Wildcard знаходить документи, які містять значення у вказаному полі, що відповідають заданому шаблону підстановки. Даний запит є подібним до пошуку за регулярним виразом, але у шаблонах підстановки підтримуються лише оператори ? (будь-який один символ) та * (будь-яка кількість символів):

    Внутрішній об'єкт, крім обов'язкового параметра value також підтримує наступні необов'язкові поля:
* case_insensitive - булеве поле: якщо має значення true, то пошук є нечутливим до регістру символів; якщо має значення false, то чутливість до регістру символів визначається налаштуваннями відображення поля (необов'язкове; значення за замовчуванням - false);

* wildcard - псевдонім для поля value, який можна використовувати замість нього; якщо у запиті будуть одночасно вказані value та wildcard, то для пошуку буде використовуватися значення з останнього у запиті поля.
    Запит Fuzzy знаходить документи, що містять у заданому полі значення, подібні до заданого. Подібність у даному запиті визначається за допомогою відстані Левенштейна (відома також як відстань редагування).
    Відстань редагування - це кількість односимвольних операцій, яка необхідна для того, щоб один терм перетворити на іншій. Допускаються наступні операції:
* заміна одного символу іншим; наприклад, для того, щоб терм box перетворити на терм fox, достатньо однієї заміни (b на f);
* видалення одного символу; наприклад, для того, щоб терм black перетворити на терм lack, достатньо одного видалення (b);
* додавання одного символу; аналогічно прикладу для видалення, щоб отримати black з lack, достатньо додати один символ (b);
* перестановка двох сусідніх символів місцями; наприклад, для того, щоб з терма cat отримати терм act, достатньо переставити місцями два сусідніх символи (c та a).
    Наприклад, відстань редагування між термами elephant та relevant дорівнює 3, оскільки щоб отримати другий терм з першого достатньо виконати три операції:
* замінити символ p на символ v - отримуємо elevhant;
* видалити символ h - отримуємо elevant;
* додати символ r на початку - отримуємо relevant.
    Для того, щоб знайти подібні до заданого значення, запит Fuzzy створює набір усіх можливих варіацій (або розширень) заданого терма в межах заданої відстані редагування. Потім запит повертає точні збіги для кожного розширення:


    Крім обов'язкового параметра value, запит Fuzzy також має додаткові необов'язкові параметри:
* fuzziness - максимальна відстань редагування для пошуку; параметр може бути заданий двома формами:
o значення 0, 1 чи 2 - константа, максимальна відстань редагування;
o AUTO:[low],[high] - максимальна відстань редагування залежить від довжини заданого значення; якщо довжина менше заданої межі low, то максимальна відстань 0, якщо довжина більше або дорівнює low та менше high, то максимальна відстань 1, якщо довжина більше або дорівнює high, то максимальна відстань 2. Значення AUTO є значенням за замовчуванням для параметра fuzziness та рівноцінне значенню AUTO:3,6.
* max_expansions - максимальна кількість розширень, що створюється запитом (значення за замовчуванням - 50);
* prefix_length - кількість символів на початку заданого значення, що не повинні змінюватися під час створення розширень (значення за замовчуванням - 0);
* transpositions - булеве значення, яке відповідає за те, чи допускається операція перестановки двох сусідніх символів місцями (значення за замовчуванням - true).

Найпростіші складені запити
    Складені запити, як сказано у пункті "Виконання запитів", можуть обгортати інші складені чи листкові запити з однією з трьох цілей:
* поєднання результатів та оцінок релевантності _score вкладених запитів;
* зміна поведінки вкладених запитів;
* перемикання контексту вкладеного запиту з контексту запитів у контекст фільтрів.
    Запит Constant_score обгортає вкладений запит (вказаний у параметрі filter), виконує його у контексті фільтрів та повертає знайдені документи, встановивши їм задану оцінку релевантності:










    Крім пришвидшення виконання фільтруючих запитів у контексті фільтрів за рахунок відмови від оцінювання релевантності, Elasticsearch також автоматично кешує результати виконання більшості таких фільтрів. Для цього в пам'яті для запиту-фільтру створюється бітова карта, яка зберігає для кожного документа відмітку про те, чи задовольняє він запит-фільтр. Наступні виконання цього запиту, замість звернення до індекса, будуть звертатися до побудованої бітової карти, таким чином зберігаючи цикли CPU та зменшуючи кількість I/O операцій, ще більше пришвидшуючи виконання запиту.
    Параметр boost встановлює оцінку релевантності, з якою будуть повернуті результати, та є необов'язковим: за його відсутності у запиті буде використано значення за замовчуванням 1.0.

    Запит Bool дозволяє поєднати декілька вкладених запитів логічним відношенням. У даному запиті передбачено чотири види вкладених запитів:
* must - документ, щоб бути повернутим, обов'язково повинен задовольняти даному запиту; запити цього виду вносять свій внесок до фінальної оцінки релевантності;
* filter - документ, щоб бути повернутим, обов'язково повинен задовольняти даному запиту; запити цього виду не враховуються у фінальній оцінці релевантності;
* must_not - документ, щоб бути повернутим, обов'язково повинен не задовольняти даному запиту;
* should - документ, щоб бути повернутим, необов'язково повинен задовольняти даному запиту, але якщо задовольняє, то більшою буде фінальна оцінка релевантності.

    Запит Bool може включати декілька вкладених запитів must, must_not чи should. Для вкладених запитів перших двох видів це означає, що документ, щоб бути повернутим, обов'язково повинен задовольняти (або не задовольняти) кожному запиту. Така поведінка дозволяє використовувати такий варіант запиту Bool (з декількома must чи filter) як аналог "І" для декількох запитів.
    Якщо у запиті Bool не вказати жодного must чи filter запиту, то документ, щоб бути повернутим, обов'язково повинен задовольняти хоча б одному запиту should. Такий варіант запиту можливо використовувати як аналог "АБО" для декількох запитів:

    За таку поведінку запиту Bool відповідає необов'язковий параметр запиту minimum_should_match, який визначає кількість вкладених запитів should, котрій документ повинен обов'язково відповідати, щоб бути повернутим. Цей параметр має значення за замовчуванням рівне 1, якщо запит має хоча б один вкладений запит should та жодного must чи filter; у всіх інших випадках значення за замовчуванням рівне 0. За бажанням, параметр minimum_should_match можливо встановити у явному вигляді, таким чином змінюючи поведінку запиту Bool за замовчуванням. Параметр може приймати значення декількох різних видів:

* позитивне ціле число - вказує на фіксовану кількість запитів should незалежно від їх фактичної кількості; наприклад, значення 3 вказує на те, що документ обов'язково повинен задовольняти хоча б трьом запитам should;
* негативне ціле число - вказує на те, що фіксована кількість запитів should є необов'язковою (тобто, загальна кількість запитів should за мінусом вказаного значення є обов'язковою); наприклад, якщо вказано значення -2 та запит містить п'ять вкладених запитів should, то документ обов'язково повинен задовольняти хоча б трьом;
* позитивний відсоток - вказує на те, що певний відсоток від загальної кількості запитів should є обов'язковим (з округленням вниз); наприклад, якщо вказано значення 75% та запит містить шість вкладених запитів should, то документ обов'язково повинен задовольняти хоча б

чотирьом

6  75% ;

* негативний відсоток - вказує на те, що певний відсоток від загальної кількості запитів should є необов'язковим (тобто, загальна кількість запитів should мінус вказана кількість відсотків є обов'язковою); даний відсоток також округлюється вниз, тому фактично кількість обов'язкових запитів можливо розрахувати з округленням вгору: наприклад, якщо вказано значення -25% та запит містить шість вкладених  запитів  should,  то  документ  обов'язково  повинен
задовольняти хоча б п'яти ( 6  6  25% або 6  (100%  25%) );
* позитивне ціле число, після якого йде знак < та будь-яке із попередніх форматів значень - вказує на те, що якщо кількість вкладених запитів should менше або дорівнює вказаному числу, то усі вони є обов'язковими, інакше застосовується значення, вказане після символу
<; наприклад, якщо вказано значення 3<80%, то при запиті, що містить один,  два  чи  три  вкладених  запити  should  всі  вони  будуть
обов'язковими, інакше обов'язковими є 80%.

    Запит Boosting обгортає два обов'язкові вкладені запити - позитивний та негативний. Всі документи, що повертаються запитом Boosting, задовольняють позитивний вкладений запит; якщо певний документ одночасно з позитивним запитом також задовольняє і негативний, то його оцінка релевантності буде знижена (але документ все одно буде повернуто):

    Як бачимо, запит Boosting відрізняється від запиту Bool саме тим, що документи, що задовольняють негативний вкладений запит, все одно потраплять до результатів, а при використанні запиту Bool, документи, що задовольняють вкладеному запиту must_not, повернуті не будуть.
    Третій, обов'язковий параметр даного запиту - negative_boost - є коефіцієнтом, що відповідає за зниження оцінки релевантності документів, що задовольняють і позитивному, і негативному вкладеним запитам. Для таких документів фінальна оцінка релевантності отримується шляхом множення оригінальної оцінки релевантності, отриманої від позитивного вкладеного запиту, на цей коефіцієнт (допустимі значення - від 0.0 до 1.0).
Завдання на лабораторну роботу
    Реалізувати інформаційно-пошукову систему, що інтегрована з системою Elasticsearch та надає можливість пошуку збережених документів за метаданими, відповідно до наступних вимог:

1. Для реалізації інформаційно-пошукової системи може використовуватись будь-який стек (мова програмування, фреймворк і так далі) технологій.
2. Для інтеграції з Elasticsearch допускається пряме використання Elasticsearch REST API або будь-яких бібліотек-обгорток.
3. Інформаційно-пошукова система може мати будь-який з перелічених інтерфейсів користувача: консольний, веб, мобільний, настільний.
4. Інформаційно-пошукова система повинна надавати користувачу Create- Read-Delete (Update не є обов'язковим, може бути реалізованим за бажанням студента) інтерфейс для роботи з документами певної предметної галузі. Предметна галузь визначається відповідно до варіанту студента (див. Додаток В).
5. Документ повинен мати мінімум чотири поля різних типів (не рахуючи id), визначених відповідно до предметної галузі.
Приклад: для предметної галузі "кіно", документ може містити наступні поля:
* назва фільму (тип keyword);
* дата виходу (тип date);
* актори (масив keyword);
* касові збори (тип long).
6. Використання типу text для повнотекстового пошуку в рамках цієї лабораторної роботи не допускається.
7. Інформаційно-пошукова система повинна надавати користувачу можливість фільтрації документів, що відображаються, окремо за кожним із визначених полів. За бажанням, студент може реалізувати можливість фільтрації документів за декількома полями одночасно, використовуючи для цього складений запит bool.
8. Для фільтрації необхідно використовувати запити на рівні терма самого Elasticsearch. Зчитування з Elasticsearch всіх документів та їх фільтрація

у пам'яті розробленої інформаційно-пошукової системи не допускається.
9. Обов'язкові запити на рівні терма для реалізації: term (наприклад, для полів keyword), range (наприклад, для полів date, integer) + один складний ("дорогий") запит, визначений відповідно до варіанту студента (див. Додаток В). За бажанням, студент може реалізувати інші типи запитів.
